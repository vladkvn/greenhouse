# 01 — Архитектура

## Распределение ролей по железу

| Железо            | Роль                       | Что на нём крутится                                   |
|-------------------|----------------------------|-------------------------------------------------------|
| Jetson Orin Nano  | Мозг (Linux + ROS2)        | Драйвер лидара, SLAM, Nav2, машина состояний, фьюжн   |
| ESP32             | Низкоуровневый контроль РВ | PID/ШИМ моторов, watchdog, аварийный стоп, IMU         |
| L298N             | Силовой драйвер моторов    | Преобразует ШИМ ESP32 в питание моторов               |
| RPLIDAR           | Основной сенсор            | Скан 2D, прямо в Jetson по USB                         |

Принцип: всё, что требует жёсткого реального времени и безопасности — вниз, на ESP32.
Всё, что требует вычислений и карты — вверх, на Jetson. Связь между ними — один чёткий контракт (см. ниже).

## Три слоя

### 1. Слой безопасности (ESP32, наивысший приоритет)
Работает без карты и без Jetson. Если он сработал — робот стоит, что бы ни «думал» верхний уровень.
- **Watchdog:** нет команды `cmd_vel` дольше N мс (напр. 300 мс) → моторы в стоп.
- **Лимит тока / времени ШИМ:** защита от заклинивания.
- **Аварийный стоп:** кнопка и/или бампер заводятся прямо на ESP32 (когда появятся).

### 2. Слой навигации (Jetson)
- Лидар → SLAM (карта + локализация) → Nav2 (глобальный план + локальный объезд).
- **Запретные зоны** — costmap-фильтры Nav2 (keep-out / speed-limit). Не требуют сканирования всей территории.

### 3. Слой поведения (Jetson)
- Машина состояний: `idle / manual / mapping / patrol / return / charging(stub)`.
- Реализация — BehaviorTree (внутри Nav2) + lifecycle-ноды для «поднять, но не активировать» режим.
- Ручной канал переключения режима для отладки: `ros2 service call` / топик / кнопка джойстика.

## Ноды ROS2 (целевой состав)

```
sllidar_ros2          → /scan              (драйвер RPLIDAR)
slam_toolbox          → /map, TF map→odom   (картирование + локализация)
rf2o_laser_odometry   → /odom (часть)       (одометрия по лидару — пока нет энкодеров)
imu_node (micro-ROS)  → /imu                (ориентация с BNO055)
robot_localization    → фьюжн /odom + /imu  (EKF, сглаженная поза)
nav2 (bringup)        → /cmd_vel            (планирование + объезд)
base_controller       → колёса             (cmd_vel → ШИМ; на ESP32 через micro-ROS)
state_machine         → режимы             (поведение)
teleop_twist_keyboard → /cmd_vel           (ручное вождение для тестов)
```

## Поток данных

```
        RPLIDAR ──/scan──┐
                         ├─► SLAM Toolbox ──/map, TF──► Nav2 ──/cmd_vel──► [micro-ROS] ──► ESP32 ──► L298N ──► моторы
   лидарная одометрия ───┤                              ▲                                   │
        IMU ──/imu───────┴─► robot_localization ──/odom─┘                                   │
                                     ▲                                                      │
                                     └──────── (в будущем) энкодеры ◄───────────────────────┘
```

Пунктир «энкодеры» — апгрейд: когда появятся, замкнут контур одометрии и сделают `/odom` честным.

## Системы координат (TF)

`map → odom → base_link → {laser, imu}`

- `map` — глобальная, origin в точке старта робота (физическая нулевая точка не нужна).
- `odom` — непрерывная, дрейфует (особенно без энкодеров); поправляется SLAM-ом.
- `base_link` — центр робота; от него смещения до лидара и IMU (статические TF).

## Как это закрывает «серые зоны»

- **Тест по частям:** каждая нода запускается/убивается отдельно. Можно гонять моторы без лидара и наоборот.
- **Режимы:** lifecycle + ручной канал — поднимаешь и дёргаешь режимы руками, автопереходы включаешь по одному.
- **Запретные зоны без полного скана:** keep-out полигоны в costmap + физический слой безопасности на ESP32 как дубль.
- **Нет дока/нулевой точки:** origin при старте; зарядка — заглушка (см. `05-test-plan.md`, этап режимов).
