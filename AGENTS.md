# GreenHouse Robot — playbook для агентов и разработчиков

Этот документ фиксирует, **как** мы строим проект модульной системы робота для теплицы (ROS 2 на Raspberry Pi + multi-robot backend на FastAPI + MQTT).

См. также [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) для целевой архитектуры и связей между пакетами.

## Принципы архитектуры

### Contract-first

- Контракты модулей (типы сообщений домена, интерфейсы сенсоров/навигации и т.д.) живут в [`packages/contracts`](packages/contracts/).
- Реализации **сменяемы**: реальный лидарайвер, mock, симулятор — каждый удовлетворяет одному и тому же `Protocol`.
- Доменные типы на границах валидируются (Pydantic), а не «сырые» словари.

### Adapter pattern для ROS 2

- ROS 2 — **транспорт и интеграция** (топики, actions, ноды).
- Бизнес-логика и оркестрация **не** должны напрямую зависеть от деталей `rclpy` там, где достаточно контракта: адаптер переводит ROS ↔ контракты.

### Mock-first

- У каждого значимого интерфейса из `contracts` появляется mock-реализация в [`packages/sim`](packages/sim/) **до** или **параллельно** появлению железа.
- Разработка и тесты не блокируются отсутствием лидаров/камер/моторов.

### Маленькие вертикальные срезы

- Один шаг = один модуль (или один чёткий слой) + его README + при необходимости mock + проверка типов/линта для затронутых пакетов.
- Не смешивать в одном PR «всю навигацию и весь backend».

### Типобезопасность

- На границах модулей: `typing.Protocol` + Pydantic-модели.
- Не использовать небезопасные приведения типов (`cast` без доказанной корректности, `Any`, подавления проверок) без явного согласия в треде.

### Документация границ

- Каждый модуль в `packages/robot` и `packages/backend` имеет `README.md` с: назначением, ссылкой на контракты, зависимостями, планируемыми реализациями, топиками ROS / MQTT (если применимо), известными сбоями.

### Контекст теплицы

- Indoor, 2D-навигация, низкая скорость, **без GPS** как обязательного источника.
- Требования к безопасности и остановке при потере локализации / цели — описывать в модуле оркестрации и в контрактах команд.

### Multi-robot с первого дня

- Все идентификаторы и сообщения к backend включают **стабильный `robot_id`**.
- Топики MQTT и схемы payload согласованы с [`packages/contracts`](packages/contracts/) (константы имён + DTO).

## Рабочий процесс

1. Меняем или добавляем контракт в `packages/contracts`, если меняется граница модулей.
2. Обновляем README затронутого модуля и при необходимости [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
3. Реализация / mock в `packages/robot`, `packages/backend` или `packages/sim`.
4. После шага: для затронутых Python-пакетов — `ruff` / `mypy` (когда настроены) и тесты, если есть.

## Где что лежит

| Путь | Назначение |
|------|------------|
| `packages/contracts` | Protocol + Pydantic + константы MQTT/API |
| `packages/robot` | ROS 2 workspace, onboard-модули |
| `packages/backend` | FastAPI + интеграция с MQTT/БД (по мере реализации) |
| `packages/sim` | Mocks и будущая симуляция (Gazebo и т.д.) |
| `docs/ARCHITECTURE.md` | Общая схема, диаграммы, roadmap |
| `infra/` | Docker Compose, брокер и т.д. (по мере появления) |
